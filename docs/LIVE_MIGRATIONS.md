# Live migration execution and verification

factgraph v0.5 adds an **optional live migration harness** on top of the v0.4 semantic diff and migration planner.

The planner remains file-only. Live execution is a separate command and requires an explicit database connection plus explicit safety opt-ins.

```text
before model
   |
   v
canonical before target schema ---- fixture population
   |                                  |
   +---------------+------------------+
                   v
            isolated namespace
                   |
          semantic migration plan
                   |
          target operation policy
                   |
     preflight -> execute -> introspect
                   |
                   v
          compare to after target plan
```

## Command

```bash
factgraph live-migrate before.fg after.fg \
  --hints hints.json \
  --fixture fixture.pass.json \
  --out-dir artifacts/live_migration \
  --postgres-dsn postgresql://... \
  --mongo-uri mongodb://... \
  --allow-risky
```

Options:

- `--allow-risky` permits `requires_data_check` operations **only after their generated preflight succeeds**.
- `--allow-destructive` additionally permits destructive operations. It does not make manual operations executable.
- `--keep` leaves the isolated PostgreSQL schema or MongoDB database in place for inspection.
- without a DSN/URI the target report is written as `not_run`; absence of a service is never counted as a pass.

The command writes:

```text
postgres.json
mongo.json
LIVE_MIGRATION.json
```

No result exists only in terminal output.

## Execution policy

The generic executor has four behaviors:

| Safety | Default | With opt-in |
| --- | --- | --- |
| `safe` | execute if the planner marked it automatic | same |
| `requires_data_check` | blocked | preflight, then execute only if the gate passes |
| `destructive` | blocked | execute only with `--allow-destructive`; preflight is impact evidence, not a zero-row gate |
| `manual` | always blocked | always blocked |

A preview generated by `factgraph migrate` is still only a preview. The live executor independently reads the target migration plan and applies this policy.

## Isolation

### PostgreSQL

Each run creates a deterministic temporary schema named like:

```text
fg_mig_<hash>
```

The harness:

1. creates the canonical **before** schema;
2. loads the optional fixture;
3. verifies that the live schema matches the before target plan;
4. enters a PostgreSQL transaction for the migration;
5. executes safe staging operations;
6. evaluates each gated preflight before its gated operation;
7. rolls the entire migration transaction back on a preflight or execution failure;
8. introspects the resulting schema;
9. compares it structurally with the intended after target plan;
10. drops the temporary schema unless `--keep` was used.

This means a PostgreSQL preflight failure is expected to leave the before schema intact.

### MongoDB

Each run creates a deterministic disposable database named like:

```text
fg_mig_<hash>
```

The harness uses PyMongo APIs rather than evaluating generated JavaScript text. Therefore MongoDB migration operations carry a structured `parameters` object alongside their human-readable command preview.

Generic MongoDB DDL/document migration is **not treated as one transaction**. On failure, factgraph does not claim rollback. Instead the harness discards the isolated database unless `--keep` is used.

That distinction is part of the execution report.

## Live verification

The executor does not treat “all commands returned success” as enough.

### PostgreSQL verifier

It introspects the isolated schema using PostgreSQL catalogs/information schema and compares:

- table names;
- column order, type, and nullability;
- primary keys;
- unique constraints;
- CHECK constraints under a canonical normalization;
- foreign-key source/target columns.

### MongoDB verifier

It compares:

- collection names;
- collection validators;
- non-`_id` index key shapes;
- index uniqueness.

Verification is against the **target projection of the after model**, not against source strings.

If the plan contains blocked/manual operations, the run is reported `completed_partial` rather than claiming the after target was fully reached.

## Migration fixtures

A live fixture has this versioned format:

```json
{
  "format": "factgraph-live-migration-fixture-v1",
  "postgres": {
    "setup_sql": [
      "INSERT INTO person (...) VALUES (...)"
    ]
  },
  "mongo": {
    "setup": [
      {
        "op": "insert_one",
        "collection": "person",
        "document": {"person_id": "p1"}
      }
    ]
  }
}
```

Fixtures are intentionally target-facing test data. They are not presented as a general semantic instance-migration format.

`examples/migrations/safe_risky/` contains:

- `fixture.pass.json` — old-schema data that satisfies the new requiredness/value/uniqueness constraints;
- `fixture.fail.json` — old-schema-valid data that violates the new required `displayName` and `Membership(member)` max-one rule.

With `--allow-risky`, the first should reach the after target. The second should stop at a generated preflight.

## Disposable Docker environment

The existing conformance Docker Compose file also supplies the services for migration execution:

```bash
./scripts/start_conformance_services.sh
./scripts/run_live_migrations.sh
./scripts/stop_conformance_services.sh
```

Optional Python dependencies:

```bash
pip install -e '.[conformance]'
```

## What v0.5 does not claim

The live harness is deliberately narrower than a production migration orchestrator.

It does **not** provide:

- zero-downtime deployment choreography;
- application version coordination;
- general backfill expressions;
- arbitrary type conversion;
- automatic execution of `manual` operations;
- resumable distributed migrations;
- production lock/latency budgeting;
- arbitrary existing-database reverse engineering.

The purpose of v0.5 is to answer a smaller question with evidence:

> Given a before model, an after model, and factgraph's own target projection, do the generated migration operations actually transform a disposable live target into the structure factgraph says they should—and do the safety gates reject known-invalid old populations before a gated change is applied?
