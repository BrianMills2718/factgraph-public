# v0.15 — pinned third-party LinkML → PostgreSQL audit

## Why this milestone exists

v0.14 proved that Factgraph can execute source-semantic witnesses against externally supplied PostgreSQL DDL, but its checked-in preserving/weakened examples were still constructed inside this repository.

v0.15 introduces the first experiment in which the physical artifact is generated by an **independently developed conversion pipeline**.

The selected first pipeline is LinkML's SQL Table Generator because:

- LinkML is an established external schema language rather than a Factgraph fixture format;
- its official documentation supports SQL DDL generation and a PostgreSQL dialect;
- Factgraph already has a bounded LinkML semantic importer that preserves the specific source constraint being tested;
- the generator can run in hosted CI and produce an opaque SQL artifact that Factgraph did not synthesize.

## Pinned provenance

External project: **LinkML**

Pinned Python package: **`linkml==1.11.1`**

Release:

- https://github.com/linkml/linkml/releases/tag/v1.11.1

Generator documentation:

- https://linkml.io/linkml/generators/sqltable.html

Pinned generator source:

- https://raw.githubusercontent.com/linkml/linkml/v1.11.1/packages/linkml/src/linkml/generators/sqltablegen.py

Generation command:

```bash
gen-sqltables --dialect postgresql value_range.yaml
```

The source and generated DDL are retained as separate files in the CI evidence artifact. Factgraph does not call its own PostgreSQL emitter to create or patch this DDL.

## Source semantic rule

`examples/external_pipelines/linkml_1_11_1/value_range.yaml` contains a lower-case `person` class so the bounded v0.14 unquoted identifier mapping can bind it without guessing or case-folding heuristics.

The relevant LinkML slot is:

```yaml
age:
  range: integer
  required: true
  minimum_value: 0
  maximum_value: 130
```

The bounded LinkML importer converts this to a Factgraph value type carrying `range(0, 130)`, with zero unsupported/lossy issues for this source case.

## Falsifiable hypothesis

Inspection of LinkML 1.11.1's `SQLTableGenerator` shows construction of SQLAlchemy columns, PKs, FKs, indexes, and unique constraints. The generator code does not itself construct SQL CHECK constraints from `minimum_value` / `maximum_value`.

That observation motivates a hypothesis:

> the official LinkML → PostgreSQL DDL projection will permit the source-invalid `age = -1` state.

This is **not counted as a Factgraph finding merely from code inspection**.

The semantic finding exists only if the actual LinkML-generated artifact is applied to PostgreSQL and Factgraph's shared source-semantic witness is observed as realized.

## Execution contract

Hosted CI runs:

```bash
python scripts/run_linkml_postgres_pipeline_audit.py \
  --out-dir artifacts/external_pipelines/linkml_1_11_1 \
  --postgres-dsn "$FACTGRAPH_POSTGRES_DSN" \
  --require-generator --require-live
```

The runner:

1. verifies the installed LinkML package is exactly `1.11.1`;
2. invokes `gen-sqltables --dialect postgresql`;
3. stores stdout unchanged as `generated_by_linkml.sql`;
4. imports the original LinkML source into Factgraph's semantic kernel;
5. produces the explicit v0.14 semantic→physical mapping;
6. validates that mapping against exact source/DDL SHA-256 fingerprints;
7. applies the external DDL to isolated PostgreSQL schemas and performs mapped table/column structural preflight;
8. lowers the same source-semantic counterexample into the external layout;
9. executes it against PostgreSQL;
10. records `preserved_or_stronger`, `weakened`, or unresolved evidence independently of Factgraph's own PostgreSQL capability declarations.

The expected value-range observation is `weakened`. `--require-live` makes any unavailable/unobserved run non-successful in hosted CI.

## Local packaging behavior

The packaging sandbox intentionally does not install LinkML from the network. Running the experiment here therefore writes:

```json
{
  "status": "generator_unavailable",
  "live_observed": false,
  "passed": null
}
```

That is readiness/provenance evidence only, not a semantic finding.

## What would count as the first external finding

Only a live artifact whose provenance shows:

- `linkml==1.11.1`;
- successful `gen-sqltables --dialect postgresql` execution;
- exact generated SQL SHA-256;
- valid explicit physical mapping;
- successful PostgreSQL artifact preflight;
- the value-range obligation's shared semantic witness realized;
- `actual_value_range_observation = "weakened"`.

If PostgreSQL prevents the witness, the experiment must fail its current hypothesis and report the observed result rather than adjusting the witness.

## Scope boundary

This milestone does not claim that LinkML as a whole loses numeric ranges in every target or workflow. It audits one pinned generator, one pinned version, one source construct, and one physical target. LinkML also has separate validation/generator facilities; the question here is specifically whether the generated PostgreSQL DDL itself preserves this source obligation.
