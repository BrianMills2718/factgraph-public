# Executable conformance

v0.2 introduced a target-conformance layer whose purpose is to test whether the capability report corresponds to actual target behavior.

## Two directions are tested

For a capability reported as `native_enforced` or `emulated_enforced`, every source element must have at least one generated conformance case. `conformance/coverage.json` fails coverage if any such claim is untested.

The suite also generates **gap probes** for selected `represented_not_enforced` semantics. For example:

- a source-level total-participation `mandatory(role)` constraint should still permit an entity with no relationship row/document in the canonical PostgreSQL/Mongo mappings;
- logical `symmetric` should accept `R(a,b)` without silently creating `R(b,a)` because the adapters explicitly report symmetry as not enforced.

v0.3 extends the same discipline to value domains, frequency, subtyping, and cross-fact role-sequence constraints. This makes the capability system testable in both directions: what the compiler says is enforced, and what it says is not.

## Build-time evidence

Every ordinary build writes:

```text
conformance/
  coverage.json
  static_results.json
  live_status.json
  postgres/cases.json
  mongo/cases.json
roundtrip.json
```

`static_results.json` executes structural assertions that do not require a database, such as confirming that a normalized field becomes exactly one target column/property.

`cases.json` contains deterministic positive and negative populations ready for a live runner.

## Live execution

The core package has no runtime dependencies. Live target drivers are optional:

```bash
python -m pip install -e '.[conformance]'
```

Then either provide existing services:

```bash
PYTHONPATH=src python -m factgraph live-conformance examples/warehouse.fg \
  --out-dir artifacts/live/warehouse \
  --postgres-dsn 'postgresql://user:pass@localhost/db' \
  --mongo-uri 'mongodb://localhost:27017'
```

or use the included Docker Compose file:

```bash
./scripts/start_conformance_services.sh
python -m pip install -e '.[conformance]'
./scripts/run_live_conformance.sh
./scripts/stop_conformance_services.sh
```

All live results are written to files. The command never treats an unavailable driver/service as a successful conformance run; the JSON result records `unavailable` or `not_run` explicitly.

## Isolation

PostgreSQL uses a dedicated disposable schema per model and recreates it for each runtime case.

MongoDB uses a dedicated disposable database per model and recreates it for each runtime case.

No user application tables or collections are targeted.

## What this proves and does not prove

A successful live run supports the narrow claim that **the canonical schema generated by this compiler enforces (or intentionally does not enforce) the tested semantics on the tested server versions**.

It does not prove:

- arbitrary PostgreSQL or MongoDB schemas can be reverse engineered into the conceptual model;
- the targets are semantically equivalent in general;
- all ORM constraints are implemented;
- persistence semantics absent from GraphQL SDL are enforced elsewhere.

## Round-trip evidence

`roundtrip.json` distinguishes three things:

1. canonical source semantic round trip;
2. emitter-to-structural-reader consistency for pure target artifacts;
3. exact recovery using an explicit semantic sidecar.

The report deliberately sets `native_exact_semantic_roundtrip_claimed` to `false`. Sidecar-assisted equality is not misreported as evidence that executable SQL or the pure Mongo target schema natively stores every conceptual fact.
